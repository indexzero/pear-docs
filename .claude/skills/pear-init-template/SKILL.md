# Authoring `pear init` templates

`pear init` accepts:

- A built-in template name: `default`, `ui`, `node-compat`.
- A directory path: `pear init ./my-template ./out`.
- A `pear://` link to a staged template drive: `pear init pear://<key> ./out`.

A template is a directory tree whose filenames and file contents can contain `__name__`-style placeholders, plus a `_template.json` describing the prompts that fill those placeholders.

## When to use

- The user wants a custom scaffold (e.g. "init a chat app with my org's defaults").
- The user is publishing a template peer-to-peer.
- The user is debugging template prompts (validation, defaults, overrides).
- The user is shipping a template alongside a library (so consumers `pear init pear://<key>`).

## Quick start

```
my-template/
  _template.json
  package.json
  index.js
  ui/index.html
```

`_template.json`:

```json
{
  "params": [
    { "name": "name",    "prompt": "App name" },
    { "name": "license", "prompt": "License", "default": "MIT" },
    { "name": "main",
      "prompt": "Main file",
      "default": "index.html",
      "validation": "(v) => v.endsWith('.html')",
      "msg": "must have a .html extension" }
  ]
}
```

`package.json`:

```jsonc
{
  "name": "__name__",
  "main": "__main__",
  "license": "__license__",
  "pear": { "name": "__name__", "type": "desktop" }
}
```

`index.js`:

```js
// __name__ — generated by pear init
console.log('Hello from __name__')
```

Test locally:

```sh
pear init ./my-template ./out
```

`pear init` prompts for each param, substitutes `__name__`, `__main__`, `__license__` in every filename and file body, and writes the result to `./out`. `_template.json` is not copied.

## `params` schema

Each entry of `params` is:

| Field         | Type                  | Meaning |
| ------------- | --------------------- | ------- |
| `name`        | string (required)     | Local identifier; appears as `__name__`. |
| `prompt`      | string                | Label shown to the user. |
| `default`     | any                   | Default value if the user just hits enter. |
| `override`    | array of strings      | Path inside the project's config that, if set, overrides the user's answer. Useful for re-rendering. Example: `["pear", "gui", "height"]`. |
| `shave`       | `[n, n]` two-element  | Trim chars at the offsets after substitution. Useful for numbers that are quoted as strings: `[-1, 1]` removes wrapping quotes. |
| `validation`  | string of `"(v) => Boolean"` | Validates input; returns truthy for valid. Stringified function (Bare evaluates it). |
| `msg`         | string                | Error message shown when validation returns false. |

Example with all the fields:

```json
{
  "params": [
    {
      "name": "height",
      "prompt": "Window height (px)",
      "default": "540",
      "validation": "(v) => /^\\d+$/.test(v)",
      "msg": "must be a number",
      "shave": [-1, 1],
      "override": ["pear", "gui", "height"]
    }
  ]
}
```

`shave: [-1, 1]` lets you write `"height": "__height__"` in `package.json` and end up with `"height": 540` (number), not `"height": "540"` (string). The `-1` trims the leading `"` of `"540"`; the `1` trims the trailing `"`.

## Placeholder rules

- **Filenames:** `__name__.js` renders to `<value>.js`. The match is exact between double underscores.
- **File contents:** any occurrence of `__name__` is replaced. Use a delimiter unlikely to appear naturally (`__pear_name__` if you want to avoid clashes with project code that uses double underscores).
- `_template.json` itself is **never rendered**.

## Built-in templates as reference

```sh
pear init default ./out
pear init ui ./out
pear init node-compat ./out
```

Inspect what they generate, then mirror the pattern. The canonical collection is [holepunchto/templates](https://github.com/holepunchto/templates).

## Distributing a template peer-to-peer

```sh
cd ./my-template
pear stage production            # outputs pear://<key>
pear seed production             # keep running so consumers can fetch
```

Consumers:

```sh
pear init pear://<key> ./out
```

Once `pear release production` is run, consumers default to the release length. Use `--checkout=staged` to try unreleased changes.

## Iterating on a template

```sh
pear init ./my-template ./scratch --force      # overwrite scratch
# edit my-template/...
pear init ./my-template ./scratch --force
```

`--yes` auto-selects all defaults — useful when iterating without re-typing prompts.

## Common pitfalls

- **Invalid JSON in `_template.json`.** `pear init` errors fast; check brackets and quoting in the `validation` string.
- **Validation function as a real function, not a string.** It must be a *stringified* function. Bare evaluates it.
- **Forgetting `pear.name`.** The generated app needs either `package.json.name` or `package.json.pear.name`. Don't leave both as raw `__name__` after rendering — confirm a value comes through.
- **`_template.json` ends up in the output.** That shouldn't happen — if it does, you're not using `pear init` and instead copied the directory manually.
- **`shave` confusion.** Use `[-1, 1]` when the placeholder is wrapped in quotes and the value should not be. Don't use shave for normal string substitution.
- **Distributing a template with dev dependencies.** `pear stage` will pull them in. Run `npm prune --omit=dev` first or use `pear.stage.ignore`.
- **Forgetting `pear seed` after staging.** No one can `pear init pear://<key>` if no peer is seeding the template.
